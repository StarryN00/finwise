**分支**：`action-types-and-guided-ux`（已创建并切换）
**基线**：`main` = f318df4「方案 A · 现有实现」
**要求**：本次开发**全部提交到分支**，不要动 `main`。`main` 要保持可运行，两个方案最后要真实对比。

---

## 0. 为什么做这件事

用户反馈的两个问题，根因是同一个：

**问题一**：新类型的问题系统无法妥善处理。
**问题二**：界面缺少引导、重点不清、信息杂乱。

### 根因（有代码位置）

Palantir 三件套 Object / Link / Action，本系统**已有 Object（32 类）与 Link（8 类）**，`/portfolio` 也在。**唯独 ActionType 没有成为对象**——它散在两处：

1. `app/ontology/service.py` 里一张写死的命令名单
2. `app/issue_triage.py:classify_task` 里一条约 90 行的 if-else 链

而这条链的**兜底分支是**：

```python
result = {'route':'SYSTEM', 'human_ready': False,
          'explanation':'系统尚未形成可交给用户判断的具体问题'}
```

**新类型问题按设计不会被交给人**，它停在那里等开发改代码。这就是问题一的确切机制。

### 引导缺失是同一个洞的第二个症状

"引导"拆开是四个问题，数据源如下：

| 问题 | 数据源 | 现状 |
|---|---|---|
| 我在哪一步 | stage | 有 |
| 为什么要做 | `task_descriptors.WhyDescriptor.facts/.rule` | 有 |
| **现在该做什么** | **可用动作集合** | **没有** |
| 做了会怎样 | `effects` | 有 |

四样里三样已经算出来了，缺的第三样正是硬编码动作集算不出来的东西。所以界面只能把 9 个 panel 一起摆出来让用户自己找（`operator.js` 现有 12 处 `primary()` 调用——**当一切都是主按钮，就没有主按钮**）。

**结论：先建动作集合，引导才有地基。顺序不能反。**

## 阶段 1：ActionType 成为对象

### 1.1 契约

新增对象类型 `ACTION_TYPE`。**`fields` 直接复用 `app/task_descriptors.py` 里已有的 `FieldDescriptor`，不要重建。**

```python
ActionType:
  id                 : str        # 稳定标识，如 'confirm_statement_account'
  label              : str        # 主按钮文案，必须是具体动词（"确认流水归属"），
                                  # 禁止"确认""提交""批准"这类通用词
  scope_kind         : Literal['RECORD','ARTIFACT','GROUP','PERIOD']
  applicability      : Predicate  # 对象状态谓词 —— 唯一决定可用性的东西
  required_evidence  : list[str]  # 缺证据即不可用，并说明缺什么（不是笼统"缺资料"）
  fields             : list[FieldDescriptor]   # 复用现有定义
  decision_inputs    : list[str]  # ★ 这个决定依赖哪些输入 —— 决定能否批量
  effects            : list[Effect]            # 结构化，可测
  not_effects        : list[str]  # 明确不会发生什么
  permission         : str
  reversibility      : {revocable: bool, entry: str|None}
  fallback           : bool       # 是否通用兜底动作
```

`decision_inputs` 沿用既定规则：**批量的分组键必须是该动作 decision_inputs 的超集。** 银行归属的 inputs 含目标账户 → 跨账户不可批量；同类发票口径 inputs 是（单据类型 + 税务口径）→ 同类可批。这条是结构约束，不是判断题。

### 1.2 把 if-chain 逐条翻译成声明

`classify_task` 里现有约 10 个分支（PARSE / STATUS_ISSUE 红蓝票 / BILL_ACCOUNT / BILL 已有意见 / confirm_bill_business / confirm_statement_account / 业务期间 / confirm_invoice_amount / 开票日期为空 / VERIFY），逐条翻译成 ActionType 声明。

**硬性要求：行为全等。** 翻译前先对现有 `classify_task` 补一组特征化测试（用现有 49 个测试文件里的既有夹具，覆盖全部分支），翻译后同一输入必须产出同一路由结果。**这组测试是防漂移的唯一保险，先写它再动代码。**

路由改为：**对当前对象状态评估所有已声明 ActionType → 得到可用集合**。不再有 if-else 链。

### 1.3 五个通用兜底动作（本阶段的核心价值）

`fallback=True`，**不绑定任何问题类型，对任何对象、任何状态都可用**：

| id | label | effects 要点 |
|---|---|---|
| `record_judgement` | 记录业务判断 | 生成 `Decision` 对象（该类型已存在）；**不解除任何告警** |
| `suspend` | 暂挂本项 | 移出当前可办理队列，问题保留；不阻断其他业务 |
| `request_supplement` | 请求补充材料 | 必填"具体要什么"，禁止笼统"缺资料" |
| `mark_out_of_scope` | 判为不属于本期 / 不入账 | 排除出本期范围，保留依据 |
| `escalate` | 升级处理 | 转交更高权限，记录理由 |

**绝对约束：五个兜底动作的 `effects` 里都不得包含"授予账务可用"。** 它们让新问题**可办理**，不让它**可入账**。这条要有测试锁住。

### 1.4 「为什么现在轮到我」

从 `applicability` 与动作依赖关系推导出：**这一项不做会卡住什么**。

`"这一步不做，本期就不能制证"` 比任何引导文案都有效，而且它是算出来的，不是写出来的。作为 descriptor 的新字段产出。

### 1.5 阶段 1 验收

- **主验收**：构造一个系统从未见过的问题类型（例如：一份既非发票也非流水的往来对账单，字段无法映射），**不改一行代码**，它必须出现在人工队列里并有可用动作。方案 A 此处必然为 0。
- 现有测试全绿；`classify_task` 特征化测试逐例全等。
- 兜底动作不授予账务可用（专项测试）。
- 埋点：**兜底动作占比**（见 §3 风险）。

## 阶段 1.5：把 UX 变成可验收规则

**排在阶段 2（对话层）之前做。** 阶段 1 产出可用动作集合后，界面才有收敛依据；先做聊天只会把杂乱的信息架构原样搬进对话里。

五条规则写成测试进 CI：

| 规则 | 断言写法 |
|---|---|
| **R1 一屏一主** | 前端测试：mount 各状态，断言渲染出的主按钮数 **恰好为 1**。当前 `operator.js` 有 12 处 `primary()`，先压到 1，其余降次要或收起 |
| **R2 四问必答** | 后端断言（不依赖前端）：当前任务 descriptor 必须同时含 stage、`why.facts`、`why.rule`、非空可用动作、`effects`。缺任一即红 |
| **R3 无动作的数字不许出现** | 前端：每个渲染的计数元素必须带下钻目标属性。**不能下钻的数字是噪音，直接删** |
| **R4 完成即衔接** | 后端：动作执行成功的响应必须含 `next`（下一项，或"本组已完成"）。不允许把用户扔回列表自己找 |
| **R5 收起而非删除** | 前端：次要信息必须存在于可展开容器中，默认不展开。会计要查证，删掉会出事 |

R1 是最高杠杆的一条，优先。

## 1. 不可动摇的约束

- **不改 `main`。** 全部工作在 `action-types-and-guided-ux` 分支。
- **复用现有写入路径**：`parse_artifact`、`FieldDescriptor`、`Decision`、`WhyDescriptor` 都已存在，不要重建。
- **不新建第二条取值/写入路径。** 这是之前工资表卡住的原因，不要重演。
- "解析检查通过" ≠ "人工已核实" ≠ "账务可用"，三者不得合并。
- ActionType 是**声明数据**，模型不得发明动作：Agent 若参与，输出必须被 schema 约束为 `{option_id ∈ 已声明集合, 预填字段, 理由}`。越权应在结构上不可能，不靠提示词。
- 兜底动作不得授予账务可用（重申，这条最容易被绕过）。

## 3. 必须警惕的风险

**通用兜底动作会被滥用成"什么都点记录判断"**，把系统降级成一个带审计的记事本——看起来什么都能办，实际什么都没自动化。

所以阶段 1 必须同时埋 **兜底动作占比** 指标。它持续走高，说明动作集合没有在长大、复利机制空转。**这个数字比任何功能验收都重要。**

配套机制：长尾走一次兜底动作后，应产出一条 ActionType 候选提案（供后续审批成正式动作）。这是"越用越准"的真实载体——不是模型变聪明，而是**动作集合在长大**，且长得可审计、可回退。这部分属于阶段 2，本次先留出接口位置。
