## 1. 这个产品要做成什么样

代账公司的工作流，五步：资料接收 → 资料分析 → 待确认与校验 → 凭证复核 → 交付归档。

用户（开发者本人，不是财务）定死的两条口径，**不要自己改回去**：

**（一）核对看最终的科目余额表，不做逐条人工核对。**
代账会计核一期账，看的是最后的科目余额表；对不上才顺着明细往前查。用户问过多家
代账公司，这是行业实际做法。所以：**系统自己能用算术验出来的，直接算完成，不要人确认。**
让人对着 27 行点"确认一致"是仪式，仪式做多了人会不看就点，比不做更坏。

**（二）交给人的界面只有两样东西：问题描述 + 选项卡。**
用户原话：「最后给到人进行交互的形式很简单，就是问题描述和选项卡，而且不要这些重复
但是很难让人理解的多个入口设计」。不要"先点一下处理方式再进去看"的中间层。

## 2. 四种形态（这是骨架，别加第五种）

`app/materials.py:25` `PROBLEM_KINDS`，分类函数在 `:35`：

| kind | 含义 | 人要做什么 |
|---|---|---|
| `UNREADABLE` | 系统没能从原件取到数 | 补件或手工填 |
| `UNVERIFIED` | 数取到了但系统验不了／对不上 | 核对 |
| `JUDGEMENT` | 原件里本来就没有这个信息 | 业务判断 |
| `VERIFIED` | 已核对一致 | 无需处理，可抽查 |

出现第五种，说明是分类漏了，不是又要加一种形态。系统自己该做完的事
（比如解析规则升级后重读）标 `SYSTEM_KIND`，不进这四栏。

`problem_buckets()`（`:44`）给右侧那四栏的件数/条数。
**注意**：`app/problem_review.py` 的只读复核覆盖层会过滤任务，所以它必须同步重算
buckets 和 counts —— 这两处口径分叉过一次，表现是"待办数怎么改都不动"，
现在共用 `materials.review_counts()` 和 `materials.problem_buckets()`，
有回归测试 `tests/test_review_counts_single_source.py` 盯着。

**一份原件一条事项。** VERIFY 原来按 5 条记录分页，27 张进项发票变成 6 个待办 ——
分页是给对照表用的，不该定义事项身份。已改成不分页。

## 3. 界面契约

### 第三步 = 中间一张卡 + 右侧分类

`static/operator-materials.js:137` `renderProblemQueue()`：

- **中间**：当前这个问题的卡片本身。顺序固定：标题与一句话描述 → agent 建议与
  「我有其他处理方式」自由输入 → 选项卡 → **默认折叠的「原件详情」**。
- **右侧**：上面一行办理状态（这件事归谁），下面四类问题（这是哪一类）。
  点开列出本类事项，点一条就在中间打开。
- 其余（成果、原件、账务可用、跨期、处理记录）全收进一个「更多」折叠块。

### 首页有待办时直接就是那张卡

`static/operator.js`，判断条件 `next_step.action.kind==='MATERIAL_TASK'`。
**不要改成调用 `currentTask()`** —— 它要读 `readiness()`/`progress`，首页早期渲染时
可能还没有，实测抛 TypeError（`tests/operator_home_inline.test.cjs` 盯着这一条）。

### 卡片内部

- `decisionOriginals()`（`static/operator-decision.js:106`）把原件明细**和系统自己的
  二次复核状态**一起收进折叠块。复核状态是系统的事，不该挡在处理动作前面。
- `decisionOptionsNav()`（`:95`）把通用兜底动作（记录判断／暂停办理／请求补充材料／
  标记本期不处理／转交复核）收进「其他处理方式 · N 项」，只留针对本问题的两三个。
  整张卡只有兜底动作时不折叠 —— 否则一个可点的都不剩。
- **卡片上显示模型自己那句话**。`materialGuidancePlainReason()` 原来用关键词从写死的
  模板里挑一句顶上去，模型原话被埋进「查看依据」，后果是两张不同的建议卡显示
  一模一样的文字。现在模型给的 ≤80 字就直接用，超长或缺失才退回模板。

## 4. Agent 管线

```
triage(规则)  →  problem_review(推理档模型)  →  material_guidance(建议档模型)  →  人
```

事项归系统时 `handling.owner==='SYSTEM'`，不进待办、不被推成下一步。
`_progress_with_digestion()`（`app/ontology/service.py:124`）让「资料分析」这一步在
还有事项归系统时停在进行中 —— 否则界面上「资料分析 ✓」会和第三步里一堆
「等待系统检查」同时成立，自相矛盾。

### 分档配置（`app/config.py`）

三件事按同一套分档，`model_for` / `tokens_for` / `timeout_for`：

| 档 | 模型 | 额度 | 超时 |
|---|---|---|---|
| 推理（STRUCTURE_PLAN / PROBLEM_REVIEW / PAYROLL_MAPPING） | `deepseek-v4-pro` | 8000 | 180s |
| 视觉（SCANNED_DOCUMENT） | `deepseek-flash`（只有它支持图像理解） | 16000 | 180s |
| 其他（含 MATERIAL_GUIDANCE） | `deepseek-flash` | 4000 | 45s |
| **全量模式下**（除视觉档） | — | 8000 | 180s |

**这一段是本次最大的发现，务必理解**：额度不够的表现是
`输出不是合法 JSON`，而不是"模型答不上来"。DeepSeek 会先花一截额度在推理上，
答案还没开始写就到顶，返回**空内容** + `finish_reason=length`。

- 原来所有档都用 `FINWISE_AGENT_MAX_TOKENS=1200` → **复核 30 条全失败、建议 23 条全失败**，
  界面上只显示「分析失败 · 调用方式未知」，查了很久。
- 同一条真实请求对比：1200 → 截断空内容；8000 → 完整返回。
- gateway 现在会把 `finish_reason` 和内容开头一并交出来（文本档与图像档都是）。

### 不要再吞异常

`problem_review.run_once()` 原来 `except Exception: pass` 式地把原因丢掉。
现在原因落到 `result.reason` 和 `ModelRun.failure_reason` 并打日志。
`material_guidance` 的本地校验失败带专门代码（`OPTION_NOT_IN_CLOSED_SET` /
`INVALID_EVIDENCE_REFS` / …，见 `CandidateRejected`），schema 失败带异常类名。
**这些代码都是服务端自己的常量，不含模型输出内容** —— 边界没有放松。

### 全量数据模式

`FINWISE_AGENT_SEND_FULL_RECORDS`（本机 `.env` 已打开，**代码默认关闭**）。

打开后 `full_packet()`（`app/material_guidance.py:225`）把整条记录交给模型：
`values`（摘要、往来单位、金额、账号、日期）、`issues` 原文、`comparison`
（原值 + 提取值 + 单元格定位）、真实选项标签、文件名与期间。复核档的字段
同时带 `source_value/value/region`。用户自己写的意见也原样送，不再枚举成意图。

关闭时走 `safe_packet()`（`:269`），模型只看得到字段名和有界枚举。

**为什么要有这个开关**：脱敏包里模型看不到任何业务内容，所以不管什么问题，
它能给的都是"缺字段，去要材料" —— 实测 20 条建议几乎全落在同一个选项上。
质量差别（同一批数据）：

- 脱敏：「付款记录缺少银行账户信息，建议请求补充可核验的账户资料。」×20
- 全量：「对账单未显示企业账户名称，无法确认流水归属账户；建议索取开户信息或对账单抬头页逐条核对。」
  「记录日期疑似落在 9 月、与已核定本期不符，可先标记本期不处理。」
  「对账单对方账号出现两种识别结果，且缺本方企业账户信息。」

**这是把客户财务数据发给 DeepSeek**，所以默认关闭，由部署方明确打开。
不要把默认值改成 true。

### 提示词

`app/ontology/gateway.py`，按 stage 分支。建议档要求：
**一句话说清问题是什么、建议怎么处理，中文 60 字以内，不得出现 `record-N`、
英文字段名或"脱敏/门禁/放行"这类内部说法，边界免责不写进 reason**（界面另有固定说明）。
改这条之前模型会写 200 字内部话，代账会计看不懂也读不完。
提示词版本：`material-guidance-prompt-v3`、`problem-review-prompt-v2`。改了要升版本，
旧结果会自动作废重跑。

## 5. 算术核对（决定什么不用人确认）

`app/reconcile.py` 的 `_total_from_verified_inputs()`：价税合计没有可比的整表合计时，
只要**净额合计已 MATCH、税额合计已 MATCH，且每条记录的价税合计确实等于自己的
净额加税额**，就判 MATCH。两种情形都走这里 —— 原件根本没这一列（系统相加得出），
以及原件有这一列但没有唯一整表合计（后者的逐条相加是对原件那一列的真正交叉核对，
比前者更强）。任何一行加不平就退回"无法验证"，不放宽。

`materials.arithmetic_ok()`（`:13`）：`parse_checks.overall in {MATCH, PASS}`。
整页记录都通过时 VERIFY 任务标 `optional`，不进待办计数、不被推成下一步，
但事项保留 —— "有问题顺着明细往前查"的入口不能没有。

实测效果：荣鼎坤 2026-08 待你处理 **28 → 0**，仍需核对 **21 条 → 0**，
待办任务 **38 → 4**。

复核判成 `SYSTEM_REVIEW` / `INSUFFICIENT` 之后，事项仍然归系统，没有往前走到人。
