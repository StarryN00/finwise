# FinWise Ontology 智能财务系统开发计划

版本：v1.0  
适用范围：绿地开发，不绑定任何既有 FinWise 实现  
对应产品设计：[PRODUCT_DESIGN.md](PRODUCT_DESIGN.md)

## 1. 开发目标

本计划的目标不是尽快做出一个能够“生成凭证”的页面，而是逐步建立一套具备以下能力的智能财务系统：

```text
事实可信
对象稳定
关系可验证
规则可复用
动作可控制
结果可回放
交付可追溯
```

第一条完整业务链以“采购业务”为纵向切片，覆盖：

```text
合同/发票/入库/付款
→ 事实记录
→ 采购业务事件
→ 采购处理组
→ 证据与规则
→ 对账
→ 凭证草稿
→ 人工复核
→ 分组交付
```

首个切片完成后，再扩展销售、工资、费用、税款、资产和资金业务。

## 2. 开发原则

### 2.1 以最小验收单元推进

每个开发单元必须同时具备：

1. 一个明确的新能力。
2. 一个可观察的正向场景。
3. 一个必须失败的负向场景。
4. 一个可追溯或可回放场景。
5. 明确的输入、输出和禁止事项。

“代码完成”“接口返回 200”或“页面能显示”不等于单元验收通过。

### 2.2 先建设事实，再建设智能

开发顺序固定为：

```text
Scope 与版本
→ 原始资料与事实记录
→ 业务事实与业务事件
→ 业务处理组与证据关系
→ 规则与确认
→ 对账与凭证
→ 命令授权与交付
→ Agent 与对话
```

### 2.3 Agent 不得成为事实来源

Agent 只能产生候选解释、候选关系和候选规则。正式事实、正式关系、正式规则、正式凭证和归档状态必须通过确定性规则与授权动作产生。

### 2.4 每个状态都必须有事实依据

任何状态变化都必须能回答：

```text
谁改变的
改变了哪个对象
基于什么证据
使用了哪个版本
通过了什么门禁
实际产生了什么结果
```

### 2.5 不以“全量自动化”为目标

优先实现：

```text
自动处理安全业务
批量确认重复规则
人工处理高风险异常
```

不追求把所有业务都变成无人确认。

## 3. 验收等级

每个开发单元需要标记验收等级，不能混用：

| 等级 | 含义 |
|---|---|
| L1 单元验收 | 对象、规则、命令和接口的单元/集成测试通过 |
| L2 场景验收 | 使用固定业务样本完成一条隔离业务链 |
| L3 真实智能验收 | 使用真实模型或真实 Harness，明确记录 `mock=false` |
| L4 部署验收 | 在目标部署环境完成同一组验收 |
| L5 生产验收 | 真实企业、真实权限和真实交付边界验收 |

L1 通过不能宣称 L3、L4 或 L5 通过。

## 5. 开发任务与最小验收目标

## T00：项目骨架与开发基线

### 目标

建立可重复启动、测试和记录结果的项目骨架。

### 交付物

- 应用服务和数据库启动方式
- 配置模板
- 数据库迁移入口
- 测试运行入口
- 本地开发说明
- 验收报告目录

### 最小验收

- 空环境可以完成初始化并启动健康检查。
- 空数据库可以执行迁移并重复执行而不产生错误。
- 测试可以区分单元、集成、场景和真实智能测试。
- 新开发者只按 README 就能启动项目。

### 必须失败

- 缺少必要配置时不能启动为“假成功”。
- 测试服务不能连接到生产数据源。
- 未初始化的数据库不能被当成已经具备账套基线。

## T01：Ontology 契约与不变量

### 目标

把产品设计中的对象、属性、关系、状态和动作定义成可验证的系统契约。

### 首批核心对象

```text
Scope
AccountingBook
AccountingPeriod
BaselineSnapshot
SourceArtifact
FactRecord
BusinessFact
BusinessEvent
ProcessingGroup
Evidence
Decision
RuleInstance
VoucherVersion
DeliveryPackage
ProcessingRun
```

### 首批核心关系

```text
DERIVED_FROM
SUPPORTS
MATCHES
BELONGS_TO
APPLIES_TO
CONFLICTS_WITH
GENERATES
VALIDATES
```

### 首批不变量

```text
所有对象必须带 Scope
原始资料不可被覆盖
事实与 Agent 建议分离
已交付对象不可原地修改
同一来源事实只能有一个有效主归属
新 Run 不得修改旧 Run 的历史结果
```

### 最小验收

- 每个对象都有唯一标识、版本和 Scope 定义。
- 未声明的关系类型不能写入系统。
- 不满足不变量的测试数据会被拒绝。
- 对象契约变更必须有版本号和兼容策略。

## T02：Scope、时间与版本基础设施

### 目标

建立企业、账套、期间、基线和时间版本的强边界。

### 交付范围

Scope：

```text
tenant_id
organization_id
legal_entity_id
ledger_id
accounting_period_id
baseline_id
```

时间：

```text
valid_time
accounting_time
observed_time
decision_time
effective_time
```

### 最小验收

- A 企业用户无法读取 B 企业对象。
- A 账套的对象无法通过修改请求参数访问 B 账套。
- 期间外的资料会被标记为期间异常，不会自动进入当前期间。
- 修改对象会产生新版本，旧版本仍可读取。
- 关闭期间拒绝普通写操作。

### 必须失败

- 只提供对象 ID、不提供 Scope 的查询必须失败。
- 缺少期间的账务动作必须失败。
- 使用旧版本提交写操作必须返回版本冲突。

## T03：SourceArtifact 原始资料接收

### 目标

保证原始资料可留存、可去重、可追溯、不可被模型覆盖。

### 交付范围

- 文件接收
- 文件哈希
- 来源渠道
- 上传人和时间
- 文件期间
- 原始文件存储
- 解析状态
- 资料处置状态

### 最小验收

- 上传一个采购发票文件后，原始文件、哈希和上传信息可查询。
- 同一文件重复上传不会产生两个有效原始文件。
- 原始文件下载内容与接收内容一致。
- 删除请求不会物理覆盖原始资料，只能按政策转为不可用或归档状态。

### 必须失败

- 文件哈希冲突时不能静默覆盖旧文件。
- 文件期间与当前处理期间冲突时不能直接进入账务处理。
- 模型调用不能修改 SourceArtifact 内容。

## T04：FactRecord 事实记录标准化

### 目标

把原始资料转换为结构化记录，同时保留原始定位和解析不确定性。

### 采购首个切片

支持：

- 合同记录
- 发票记录
- 入库记录
- 银行付款记录

### 每条记录必须保留

```text
source_artifact_id
source_anchor
original_value
normalized_value
parser_version
extraction_confidence
period_check
```

### 最小验收

- 能从一张发票提取发票号码、日期、购销双方、金额、税额和税率。
- 每个字段可以定位到原始文件页码、行号或区域。
- 字段解析失败时保留原始值，并标记缺失或不确定。
- 重新解析产生新版本，不覆盖旧 FactRecord。

### 必须失败

- 解析后的字段不能替代原始字段成为唯一事实。
- 缺少来源定位的记录不能进入正式业务判断。

## T05：BusinessFact 与 BusinessEvent

### 目标

建立跨 Run 稳定的现实业务事实和具体经济事件。

### 交付范围

- BusinessFact
- BusinessEvent
- EventIdentity
- 业务发生时间
- 会计归属期间
- 事实更正关系
- 冲销关系

### 最小验收

- 同一采购业务重新运行后仍能识别为同一个候选 BusinessEvent。
- BusinessEvent 身份不依赖文件行号或 ProcessingGroup ID。
- 模型判断“可能是采购”只能产生候选语义，不得直接改写 FactRecord。
- 同一事实存在两种解释时，系统保留两个候选解释并标记冲突。

### 必须失败

- 重跑不能创建第二个未标记的同一业务事实。
- 错误的 Agent 输出不能覆盖已经确认的 BusinessFact。

## T06：ProcessingGroup 与分组谱系

### 目标

将同一真实业务的多个事实记录组织为可处理的业务组。

### 交付范围

```text
ProcessingGroup
ProcessingGroupRevision
GroupMembership
GroupingDecision
GroupLineage
SourceDisposition
```

### 最小验收

- 合同、发票、入库和付款可以形成一个采购处理组候选。
- 同一供应商的三笔不同采购不会仅因供应商相同而合并。
- 一笔付款对应多张发票时，可以形成多对多候选关系，并标记待确认。
- 业务组拆分或合并会产生新版本和 lineage。
- 同一来源记录在同一记账口径下只能有一个确认后的主归属。

### 必须失败

- 分组算法重新运行不能原地覆盖已经交付的业务组。
- 同一来源事实不能同时进入两个已确认主业务组。

## T07：Evidence、关系与证据主张

### 目标

让每个业务判断和关系都具备可验证依据。

### 交付范围

```text
EvidenceItem
EvidenceSet
EvidenceClaim
SourceAnchor
MatchHypothesis
DecisionBasis
RelationRevision
```

### 最小验收

- 采购处理组可以列出支持它的合同、发票、入库和付款证据。
- 每条匹配关系都有来源、置信度、有效期和确认状态。
- 系统能区分“没有付款”和“没有找到付款证据”。
- 关系修订后，原关系仍可审计。
- 证据冲突、缺失和过期分别显示，不能合并成一个模糊失败状态。

### 必须失败

- 没有 SourceAnchor 的证据不能支撑自动结论。
- Agent 的文字解释不能单独作为 Evidence。

## T08：Decision、ConfirmationCard 与 RuleInstance

### 目标

把 Agent 建议、人工确认和长期规则严格分开。

### 规则生命周期

```text
RuleCandidate
→ ConfirmationCard
→ HumanDecision
→ RuleInstance
→ RuleVersion
```

### 最小验收

- Agent 可以针对采购处理组生成科目和税务规则候选。
- 用户可以查看原始证据、相似历史、候选规则、差异和影响范围。
- 用户确认后才产生 RuleInstance。
- RuleInstance 绑定企业、账套、业务类型、适用期间、适用条件和确认人。
- 同一批次的规则可以批量确认，但必须预览影响范围并可以撤销。
- 当前业务与历史规则冲突时，生成 RuleConflict。

### 必须失败

- RuleCandidate 不能直接参与正式账务处理。
- 置信度高不能自动把候选规则升级为 RuleInstance。
- 历史规则不能跨企业、跨账套或跨适用范围自动复用。

## T09：确定性对账与校验引擎

### 目标

建立不依赖模型的金额、税额、期间和余额校验。

### 首批检查

```text
银行付款与采购业务
发票金额与业务金额
进项税额与税率
期初与上期末
重复记录
期间一致性
借贷平衡
```

### 最小验收

- 完整采购处理组可以通过金额和税额校验。
- 付款金额与发票金额不一致时，相关业务组进入阻断。
- 税率或税额不一致时，系统显示计算差异和来源。
- 对账失败只阻断相关业务组，不阻塞其他安全业务组。
- 所有检查保存输入、公式、容差、版本、结果和原因。

### 必须失败

- Agent 不能修改校验结果。
- Agent 不能临时放宽容差。
- 对账失败不能进入可交付状态。

## T10：VoucherProposal、VoucherDraft 与 VoucherVersion

### 目标

建立从业务处理组到可复核凭证版本的账务产物链。

### 生命周期

```text
VoucherProposal
→ VoucherDraft
→ VoucherVersion
→ LocallyConfirmed
```

### 最小验收

- 规则已确认、证据完整且对账通过的采购组可以生成凭证草稿。
- 凭证借贷不平时，草稿不能通过校验。
- 修改科目或金额时创建新版本，旧版本只读保留。
- 每条分录可追溯到业务组、证据、规则和校验结果。
- 草稿不会影响正式余额、报表或税务申报数据。

### 必须失败

- 没有已批准规则不能生成可交付草稿。
- 草稿不能直接标记为正式凭证。
- 修改已确认版本不能原地覆盖。

## T11：Command、Policy、Authorization 与 Audit

### 目标

建立不可绕过的对象级命令授权层。

### 命令链

```text
CommandIntent
→ AuthorizationDecision
→ PreconditionCheck
→ StateTransition
→ EffectRecord
→ AuditEvent
```

### 首批命令

```text
confirm_baseline
approve_rule
confirm_grouping
suspend_group
rerun_group
generate_draft
validate_draft
revise_voucher
release_delivery
export_package
close_period
lock_period
```

### 最小验收

- 无权限用户无法执行规则确认、凭证复核、导出或锁账。
- 每个命令都校验对象 Scope 和对象版本。
- 重复提交同一命令不会产生重复效果。
- 旧版本命令会被拒绝并返回版本冲突。
- 审计记录包含操作人、对象、证据、前后状态和实际效果。
- 确认、复核、导出和锁账可以配置职责分离。

### 必须失败

- Agent 不能直接调用正式账务写接口。
- 只有 API Token 不能代表具备对象级操作权限。
- 状态改为 `CONFIRMED` 但实际效果未产生时，不能报告为成功。

## T12：ProcessingRun、重试与回放

### 目标

保证分析、重试和重新分析不会污染事实、业务组和凭证历史。

### 最小验收

- Run 固定输入资料、基线、规则、模型和 Schema 版本。
- 失败任务可以从明确节点重试。
- 取消或超时任务的迟到结果不会写入当前有效 Run。
- 重新分析生成新 Run，旧 Run、旧业务组和旧凭证版本仍可查询。
- 使用相同输入和版本可以重放并比较结果。
- 页面默认只展示最新有效 Run，但历史 Run 可审计。

### 必须失败

- 新 Run 不能覆盖旧 Run 的最终结论。
- 旧任务结果不能通过延迟回调修改新版本。

## T13：DeliveryPackage、外部回执与期间归档

### 目标

闭合本地确认、导出、外部导入、期间关闭和锁账的生命周期。

### 生命周期

```text
DELIVERABLE
→ DeliveryPackage
→ ExportCreated
→ ExternalAckPending
→ ExternalImported
→ PeriodClosed
→ PeriodLocked
```

### 最小验收

- 安全业务组可以单独生成交付包。
- 异常业务组不影响安全业务组部分交付。
- 导出包固定凭证版本、业务组范围和生成时间。
- 外部回执与导出批次和凭证版本绑定。
- 相同回执重复到达不会重复记账。
- 没有外部回执时不能标记为外部导入成功。
- 所有异常关闭后才能执行完整期间归档。

### 必须失败

- `PARTIAL_DELIVERY` 不能标记为完整归档。
- 本地确认不能直接等同于外部账务已完成。
- 外部导入后不能原地修改已导出的凭证版本。

## T14：Agent Gateway

### 目标

为所有 Agent 提供统一、脱敏、可校验、不可越权的调用边界。

### Gateway 职责

- 输入白名单
- 原始资料脱敏
- Scope 注入和校验
- 模型版本登记
- 输出 Schema 校验
- 置信度格式校验
- 证据引用校验
- 禁止越权动作
- ModelRun 审计

### 最小验收

- Agent 收到的是允许字段和必要局部证据，不是完整原始数据库。
- 输出必须符合统一结构：

```json
{
  "status": "PROPOSED",
  "summary": "",
  "confidence": 0.0,
  "items": [],
  "evidence": [],
  "risk_level": "",
  "next_action": ""
}
```

- 非法 JSON、缺少证据或越界 Scope 会使任务暂停。
- 每次调用保存模型版本、输入摘要、输出摘要和校验结果。
- Agent 无法访问正式凭证写入命令。

### 必须失败

- Gateway 不能用“修正后的假 JSON”掩盖模型非法输出。
- 模型不可用时不能使用伪造结果继续流程。
- `confidence` 不能单独触发正式账务动作。

## T15：受控 Agent 能力

### 目标

在稳定对象和命令层之上接入 Agent，而不是让 Agent 决定系统结构。

### 开发顺序

1. 资料理解 Agent
2. 业务事件 Agent
3. 关系与分组 Agent
4. 规则建议 Agent
5. 异常解释 Agent

### 最小验收

- 资料理解 Agent 只能创建解析建议和字段缺口。
- 业务事件 Agent 只能创建候选 BusinessEvent。
- 分组 Agent 只能创建候选 GroupMembership 和 GroupingDecision。
- 规则 Agent 只能创建 RuleCandidate 和 ConfirmationCard。
- 异常 Agent 只能解释已有异常，不能关闭异常。
- 所有 Agent 输出都能追溯到 ModelRun 和 Evidence。

### 必须失败

- Agent 不能直接确认 BusinessFact、RuleInstance 或 VoucherVersion。
- Agent 不能直接执行导出、归档和锁账。
- Agent 失败不能使业务状态伪装成成功。

## T16：对象工作台与确认体验

### 目标

让用户围绕业务对象工作，而不是围绕文件和 Agent 任务工作。

### 首批页面

1. 期间工作台
2. 业务处理组详情
3. 确认卡
4. 凭证版本详情
5. 异常事项详情
6. 交付和归档详情

### 最小验收

- 期间工作台能显示企业、账套、期间、当前 Run、待确认事项和可交付业务组。
- 业务处理组详情能查看来源、证据、关系、规则、对账和凭证版本。
- 确认卡先展示原始证据和差异，再展示 Agent 建议。
- 用户能看到当前状态和下一步可执行动作。
- 页面不把 Agent 建议显示成正式规则或正式凭证。

### 必须失败

- 页面不能只用一个“处理中”状态掩盖具体阻断原因。
- 不能因为有草稿就显示“正式凭证可交付”。
- 页面不能展示没有 Scope 的跨企业对象。

## T17：Ontology 查询与对话入口

### 目标

让用户直接围绕对象、关系和状态提问。

### 首批问题

```text
哪些采购业务没有匹配付款？
哪些业务组缺少入库证据？
这笔付款为什么暂挂？
哪些规则与历史不一致？
哪些业务组可以先交付？
重新分析后哪些对象发生变化？
```

### 最小验收

- 系统先查询结构化对象和关系，再由 Agent 解释。
- “没有找到付款证据”不能被回答成“确定没有付款”。
- 查询结果显示对象、证据、状态和范围。
- 无证据支撑的问题必须明确回答无法确认。
- 用户不能通过对话绕过命令授权和交付门禁。

### 必须失败

- 对话 Agent 不能从原始文件自由推断并写入事实。
- 跨企业或跨账套查询必须被拒绝。
- 没有关系的对象不能被编造为已关联。

## T18：全链路回归与发布门禁

### 目标

验证系统在正常、异常、重试、跨范围和外部交付场景下仍然安全。

### 必须覆盖的负向场景

- 跨企业读取
- 跨账套写入
- 期间错配
- 期初缺失
- 重复上传
- 错误分组
- 业务组拆分和合并
- 发票与付款金额不一致
- 税额不一致
- 规则冲突
- 模型不可用
- 模型返回非法结果
- 任务取消后的迟到结果
- 重试重复写入
- 外部回执失败或重复回执
- 部分交付后尝试完整归档
- 已锁账期间普通写入

### 最小验收

- 采购纵向切片完成一条完整正向链路。
- 至少一条缺证据业务组可以被阻断而不影响安全业务组。
- 至少一条规则冲突业务组可以进入人工确认。
- 至少一次重试和一次回放通过。
- 至少一次模型非法输出被暂停。
- 至少一次外部回执重复到达被幂等处理。
- 完整归档前所有门禁和审计证据可检查。

## 6. 首个纵向切片的固定测试数据

建议建立一个不依赖真实客户的隔离测试集：

### 正常采购组

```text
一个企业
一个账套
一个会计期间
一份采购合同
一张进项发票
一条银行付款
一条入库记录
一条已确认采购规则
```

预期：

```text
形成一个 BusinessEvent
形成一个 ProcessingGroup
对账通过
生成 VoucherDraft
创建 VoucherVersion
通过复核后进入 DeliveryPackage
```

### 缺证据采购组

缺少入库记录。

预期：

```text
业务组保留
证据缺口明确
业务组阻断
其他安全业务组继续
不能进入正式交付
```

### 规则冲突采购组

历史规则是办公费，本期金额和描述疑似设备采购。

预期：

```text
生成 RuleConflict
生成 ConfirmationCard
不自动套用历史规则
```

### 跨 Scope 测试组

使用另一企业的发票、规则或缓存键访问当前企业。

预期：

```text
访问拒绝
不返回对象摘要
写入不产生副作用
审计记录保留拒绝原因
```

## 8. 发布前硬性门禁

以下条件全部满足后，才允许进入真实企业试点：

- [ ] 所有核心对象均有稳定身份和 Scope。
- [ ] BusinessFact、BusinessEvent 和 ProcessingGroup 已分层。
- [ ] 分组支持确认、拆分、合并、撤销和 lineage。
- [ ] 所有关系都有证据、版本和确认状态。
- [ ] RuleCandidate 不会自动变成 RuleInstance。
- [ ] Agent 不能直接写事实、规则、凭证和归档状态。
- [ ] 所有写操作通过命令授权层。
- [ ] 置信度不能单独触发正式账务。
- [ ] 凭证草稿、凭证版本和外部导入状态分离。
- [ ] 外部回执与导出批次和凭证版本绑定。
- [ ] 取消、超时、重试和迟到结果不会污染当前 Run。
- [ ] 历史 Run 可以使用固定版本回放。
- [ ] 跨企业、跨账套、跨期间负向测试通过。
- [ ] 重复上传、重复命令和重复回执具备幂等性。
- [ ] 缺证据、金额差异、税额差异和规则冲突能够独立阻断。
- [ ] 生产环境尚未开放无人过账和自动锁账，除非另行完成授权和验收。

## 9. 推荐执行顺序

第一批只执行：

```text
T00 → T01 → T02 → T03 → T04
```

通过后进入采购业务语义：

```text
T05 → T06 → T07 → T08
```

再建立账务和交付闭环：

```text
T09 → T10 → T11 → T12 → T13
```

最后接入智能化和用户体验：

```text
T14 → T15 → T16 → T17 → T18
```

最小可用产品不是“T00 到 T18 全部完成”，而是：

```text
T00-T13 完成
+ 采购纵向切片 L2 通过
+ Agent Gateway L3 通过
+ 关键负向场景通过
```

在此之前，系统只能称为内部开发版本，不能称为可自动记账或可生产交付系统。
