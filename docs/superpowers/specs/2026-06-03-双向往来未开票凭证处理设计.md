# 双向往来未开票凭证处理设计

## 背景

凭证生成工作台已经支持银行流水、进项发票、销项发票之间的匹配，并能对只有流水或只有发票的单边数据生成待确认凭证。现有单边流水逻辑较简单：

- 银行付款暂无发票时，默认借记 `1123 预付账款`，贷记 `1002 银行存款`。
- 银行收款暂无发票时，默认借记 `1002 银行存款`，贷记 `2203 预收账款`。
- 单边发票暂无流水时，销项发票挂 `1122 应收账款`，进项发票挂 `2202 应付账款`。

这套逻辑适合“明确客户预收”或“明确供应商预付”的单边场景，但在真实做账中会遇到另一类高频数据：同一交易对方当月既有收款又有付款，且没有对应发票。这类数据可能是资金拆借、代收代付、押金保证金、往来清算，也可能是客户或供应商的历史往来冲销。若继续按单笔流水简单推荐预收或预付，容易把非经营性往来误判成经营收入或采购预付款。

本设计用于补充凭证系统的核心处理规则，使 AI 预处理和人工确认对“有来有往但无发票”的业务更准确、更可解释。

## 目标

- 将“同一对方双向资金往来且无发票”识别为独立业务类型，而不是普通单边流水。
- 避免系统默认把所有收款归为预收账款、所有付款归为预付账款。
- 用“科目 + 辅助核算对象”管理往来单位，避免手动创建大量明细科目。
- 支持逐笔凭证、按日合并、按月同一对方归集合并三种凭证颗粒度。
- 将用户确认结果沉淀为历史规则，后续同类对方和同类摘要优先复用。

## 业务分类

### 完全匹配

银行流水和发票可以组成 1:1、1:N、N:1 或 N:N 的平衡组合。组内金额、方向、主体关系可解释，系统生成标准收入、成本、费用、税额分录。

### 差额补齐

银行流水和发票都存在，但金额无法完全对齐。系统需要解释差额来源，并推荐手续费、折扣、部分收付款、应收、应付、预收、预付或其他往来等差额分录。

### 普通单边

只有单笔或少量同向流水，且没有同一对方反向流水，也没有可匹配发票。系统按业务方向给出预收、预付、应收、应付、费用或收入暂挂建议。

### 双向往来未开票

同一交易对方在当前会计期间内既有收款又有付款，并且这些流水没有发票匹配。系统应优先判断为往来暂挂或历史往来清算，而不是默认收入、成本、预收或预付。

### 历史延续

本月数据可能冲销历史应收、应付、预收、预付或其他往来。系统在导入历史账套或存在历史凭证规则后，应提示“可能关联历史往来”，并允许用户选择历史项目。

## 识别规则

满足以下条件时，系统将交易对方归入“双向往来未开票”候选：

- 同一月度工作包内存在同一交易对方。
- 该交易对方至少有一笔收款和一笔付款。
- 相关流水没有确认匹配的发票。
- 摘要不属于已知特殊场景，例如银行手续费、税费、社保、公积金、工资、利息、平台扣费。
- 对方名称不是银行、税务机关、社保公积金机构等系统可识别公共主体。

增强判断条件：

- 如果本月收付金额可部分或全部抵消，优先提示“往来清算检查”。
- 如果历史凭证中该对方长期使用 `其他应收款` 或 `其他应付款`，优先推荐相同往来科目。
- 如果历史发票显示该对方主要是客户，收款可提示“可能客户预收或应收回款”。
- 如果历史发票显示该对方主要是供应商，付款可提示“可能供应商预付或应付结算”。
- 如果同一对方只有收款但历史存在应收账款余额，则优先提示“冲销历史应收”。
- 如果同一对方只有付款但历史存在应付账款余额，则优先提示“冲销历史应付”。

## 科目与辅助核算

不建议为每个往来单位手动创建三级科目，例如：

```text
其他应收款-上海涌杰实业有限公司
其他应付款-上海涌杰实业有限公司
```

推荐采用“会计科目 + 辅助核算对象”：

- 科目：`1221 其他应收款`、`2241 其他应付款`。
- 辅助核算对象：交易对方名称，例如 `上海涌杰实业有限公司`。
- 系统自动维护往来单位档案。
- 若企业科目设置中启用了往来单位辅助核算，凭证分录必须带辅助对象。
- 若未启用辅助核算，系统仍应在 `source_data` 中保存对方主体，便于后续升级和查询。

这样既符合会计软件常见做法，也避免科目表无限膨胀。

## 推荐分录

### 收款但无发票，且对方存在双向往来

默认建议：

```text
借：1002 银行存款
贷：2241 其他应付款
辅助核算：交易对方
```

业务说明：收到对方款项但无法证明已经形成收入或预收，应先按往来款暂挂，待人工确认是否为客户预收、应收回款、资金拆借、代收款或押金保证金。

### 付款但无发票，且对方存在双向往来

默认建议：

```text
借：1221 其他应收款
辅助核算：交易对方
贷：1002 银行存款
```

业务说明：向对方付款但没有发票或明确采购依据，应先按往来款暂挂，待人工确认是否为供应商预付、应付款结算、资金拆借、代付款或押金保证金。

### 同一对方收付可抵消

系统不应自动抵消凭证，但应生成提示：

```text
该对方当月存在双向流水，建议核查是否为往来清算、代收代付或资金拆借。确认后可按同一对方做往来核销或调整处理方式。
```

后续若用户选择“往来清算”，系统可以按同一对方展示收付汇总和净额，但正式凭证仍要保留可追溯来源。

## 凭证颗粒度

默认规则：

- 银行流水逐笔生成待确认凭证，保证银行日记账可追溯。
- 系统在同一对方、同一天、同方向、同处理方式时，提供“按日合并”选项。
- 系统在同一对方、同一月份、同处理方式时，提供“按月合并”选项。
- 合并凭证必须在来源明细中保留每一笔流水，不得只保留汇总金额。

推荐优先级：

1. 第一阶段默认逐笔生成，人工确认效率低但最稳。
2. 有历史规则且同一对方同类业务稳定时，可建议按日合并。
3. 月末整理、对账清晰且用户主动选择时，允许按月合并。

### AI 建议合并规则

系统可以由 AI 或规则引擎先筛选“适合合并”的凭证任务，但合并动作必须由用户确认后才生效。

候选范围：

- 仅纳入同一企业、同一月度工作包内的凭证任务。
- 仅纳入 `待确认` 且 `未编号` 的凭证任务。
- 已确认、已驳回、已编号或已经被合并到其他凭证的任务不参与建议合并。
- 仅纳入来源清晰的单边银行流水任务；已经与发票形成配对、差额补齐或人工重新匹配的任务不参与本阶段自动合并。

建议条件：

- 同一交易对方。
- 同一收支方向。
- 同一处理方式与非银行科目，例如均为 `1221 其他应收款` 或均为 `2241 其他应付款`。
- 摘要和金额模式没有明显冲突。
- 银行手续费、税费、社保、公积金、工资、利息、平台扣费等特殊场景不建议合并。

建议输出：

```json
{
  "suggestion_id": "稳定可复算的建议编号",
  "merge_granularity": "DAILY 或 MONTHLY",
  "counterparty_name": "交易对方",
  "direction": "INFLOW 或 OUTFLOW",
  "source_voucher_ids": ["待合并凭证ID"],
  "bank_transaction_ids": ["来源流水ID"],
  "total_amount": "合计金额",
  "recommended_summary": "合并后的凭证摘要",
  "reason": "建议合并原因",
  "confidence": 0,
  "requires_manual_confirmation": true
}
```

确认后的处理：

- 系统新建一张合并后的待确认凭证。
- 原单笔待确认任务标记为已驳回，并写入 `MERGED_BY_OPERATOR` 标记和新合并凭证 ID。
- 合并凭证的来源明细必须保留每一笔流水，不得只保存汇总金额。
- 合并凭证的分录按相同科目方向汇总金额，仍需人工最终确认。
- 若用户后续撤销合并，可通过审计记录追溯原始单笔任务并重新生成。

## 用户确认项

当系统识别为“双向往来未开票”时，凭证详情需要显示以下确认项：

- 是否确认为往来暂挂。
- 是否改为客户预收。
- 是否改为供应商预付。
- 是否冲销历史应收。
- 是否冲销历史应付。
- 是否属于资金拆借。
- 是否属于代收代付。
- 是否属于押金或保证金。
- 是否需要重新匹配发票。

确认后系统记录：

- 企业主体。
- 交易对方。
- 收支方向。
- 摘要关键词。
- 金额模式。
- 选择的处理方式。
- 借方科目、贷方科目。
- 辅助核算对象。
- 是否允许自动套用。
- 最近使用时间。

## AI 预处理要求

AI 预处理不能只按单笔流水独立判断。对每个交易对方，系统应先形成对方级上下文，再让 AI 或规则引擎给出建议：

- 本月收款笔数、收款合计。
- 本月付款笔数、付款合计。
- 本月未匹配发票数量和金额。
- 历史发票角色：客户、供应商或双向。
- 历史凭证常用科目。
- 是否存在上期应收、应付、预收、预付、其他应收、其他应付余额。
- 当前月份是否可净额抵消。

Kimi 或其他 AI 模型输出必须是结构化建议，不直接生成最终凭证：

```json
{
  "task_type": "BIDIRECTIONAL_CURRENT_ACCOUNT",
  "counterparty_ref": "对方稳定标识",
  "confidence": 0,
  "recommended_treatment": "往来暂挂",
  "debit_account": "1221",
  "credit_account": "2241",
  "auxiliary_required": true,
  "reason": "同一对方当月存在收付双向流水且无发票匹配，优先按往来款暂挂",
  "requires_manual_confirmation": true
}
```

AI 服务失败时，系统仍遵守既有规则：本次 AI 预处理中断，不伪装成本地 AI 结果。已存在数据不被覆盖。

## 前端展示要求

资金流水列表中，双向往来未开票应区别于普通单边处理：

- 来源处理显示：`双向往来` 或 `往来暂挂`。
- 凭证状态保持 `待确认`。
- 点击行进入凭证详情时，顶部显示该对方当月收付汇总。
- 来源明细中按一行一笔展示银行流水，必要时展示相关候选发票。
- AI 补齐建议明确显示：`1221 其他应收款` 或 `2241 其他应付款`，并显示辅助核算对象。

凭证详情的建议区应避免只展示“预收账款暂挂”或“预付账款暂挂”，而是根据同一对方上下文展示：

```text
建议处理：往来暂挂
原因：该对方当月存在收款和付款，且暂无发票匹配。优先按其他应收款/其他应付款挂往来，等待确认业务归属。
```

## 状态与审计

新增或补充状态建议：

- `SINGLE_SIDED`：普通单边处理。
- `BIDIRECTIONAL_CURRENT_ACCOUNT`：双向往来未开票。
- `HISTORICAL_REVIEW`：可能冲销历史往来。
- `MANUAL_TREATMENT_ADJUSTED`：人工调整处理方式。

所有处理必须写入审计：

- AI 推荐原始结果。
- 用户最终选择。
- 处理方式变更前后。
- 科目变更前后。
- 辅助核算对象。
- 被合并或被调整的来源流水。

## 验收标准

- 对昆山黛珂特 2026-04 中同一对方既有收款又有付款、无发票匹配的数据，系统不再默认全部按预收或预付处理。
- 资金流水列表可筛选出“双向往来未开票”候选。
- 凭证详情能显示该对方当月收付汇总和每笔来源流水。
- 默认分录使用 `1221 其他应收款` / `2241 其他应付款`，并带辅助核算对象。
- 人工可调整为预收、预付、应收、应付、资金拆借、代收代付、押金保证金等处理方式。
- 用户确认后的处理方式能被后续同类数据复用。
- 后端测试覆盖同一对方双向流水无发票、普通单边流水、历史规则优先级、人工调整后规则沉淀。
- 前端测试覆盖筛选、详情展示、处理方式调整、确认后进入下一条。

## 暂不开发的内容

- 不在本阶段实现完整往来账龄分析。
- 不在本阶段自动核销历史往来，只做提示和人工选择。
- 不在本阶段替代会计判断，AI 只给建议。
- 不在本阶段自动合并大批量流水为一张凭证，合并必须由用户确认。
- 不在本阶段扩展到完整现金流量表自动分类。
