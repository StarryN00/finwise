## 处理原则
固定的是交付结构、证据和安全边界，调查任务根据资料决定。有本期账时完整重建和审查；没有时形成有依据的记账候选。两者均不以借贷平衡替代业务证明，也不把复核候选当成已入账。模型执行失败与真实业务缺证分开表示。补充说明是用户提供的陈述，须保留作者及时间，不自动当作第三方原件。

## 接入与持久化

- `AutonomousMonthlyWatch` 固定当前期间任务；`AutonomousMonthlyRun` 追加记录修订、租约、轮次、状态和审查成果。
- 处理契约版本、原件、补充说明及基线版本共同产生输入指纹。服务端领取、模型心跳、提交及人工复核均检查权限/期间/当前任务；取消后迟到结果拒收。超过租约可恢复，最多三次；模型查证和修复最多三轮。
- 执行目录由服务端生成，用户 API 不能指定工作目录或提交“模型已通过”结果。执行及独立审查使用分开的工作目录，冻结文件哈希在审查前后验证。
- 正常 `create_app` 生命周期启停后台任务。Scope 使用新流程后，旧原件/问题/历史后台不再领取它；上传只存原件并接续新任务，前端不再调用旧解析。
- 通过审查后直接建立原生 `VoucherDraft` / `VoucherVersion`，来源、理由、原件定位和 run 保留；不伪造采购组、已确认期初或规则。旧修订入口拒绝自主候选；补充依据后重新分析。人工复核只记录 `LOCALLY_CONFIRMED`，不改正式余额，未实现正式交付前阻止关账。
- `autonomous_workflow` 统一投影原件、过程、问题、阶段及当前有效候选。新增资料或陈述后旧成果仅保留历史，不再作为当前可复核凭证。
- 通用 PDF 不强制通过江苏银行 OCR。银行专用确定性检查只作用于实际银行证据；其他文件由通用原件锚点和独立审查覆盖。

## 2026-09-23：最小补证与分录审阅

比较代账凭证后确认：当前结果是 `JOURNAL_REVIEW` 原账复核，不能据逐行一致宣称已验收独立做账。界面明确显示该模式。

- “需要用户补充”与“阻止当前分录确认”分开：`needs_user` 保留补充任务，`blocks_confirmation` 决定是否影响当前候选的确认。旧结果省略该字段时默认阻断；非阻断事项必须给出 `confirmation_reason`，并由独立审查的 `nonblocking_findings` 精确覆盖。不得依据金额小、代账已做或历史金额一致自动降级。
- 新运行的待补充事项必须提供 `request`：需要回答的事实、为什么影响处理、已有资料还能完成什么、最小所需依据、当期事项或首次接账基础（`PERIOD` / `ONBOARDING`）。一份答案或补充资料进入整次重查，重新核查所有关联凭证和结转。接账基础标记不等于已确认政策；上传说明仍是带作者时间的陈述。
- 确认接口再次检查当前 run、输入指纹、原件哈希、候选评估、独立审查清单及阻断事项；预览、前端隐藏按钮、模型声称通过都不能绕开门禁。正式过账和交付限制保持不变。
- 独立审查阶段完成表示审查已执行完毕；补证问题在复核阶段保留，不把“存在问题”显示成“没有做审查”。所有待补证分录可从同一列表查看、跳转到对应问题及原件。
- 老运行可显式“重新审查补证范围”，复用原件与陈述并新建运行版本；不修改旧结论，不自动把31张待补证改成通过。重新运行期间旧成果不能确认。

## 2026-09-23：第 4 步决策循环（合同 v3）

第 4 步支持“提出方案 → 用户选择 → 重算相关凭证 → 独立审查 → 再复核”。固定交付结构和证据门禁，问题与可行方案由 Agent 根据实际原件、历史及用户回应产生，不预设企业或万能暂挂科目。

- 用户可声明“现有资料已全部提供”。系统以此作为资源边界继续分析，无需强制新增附件；声明本身不证明业务事实。新上传、归档或变更原件后此声明不自动沿用，原声明保留历史。
- 待决事项须包含 `decision`：一个具体问题，以及各选项的业务标签、适用前提、依据、处理影响和后续工作；确实无法给方案时须写明当前完成边界。选项区分业务事实、会计处理选择和暂无法判断。可推荐但不默认勾选。
- 服务端仅接收当前运行、事项与选项 ID，保存已审查选项的完整快照、作者、时间和用户确认。拒绝过期、伪造、未经审查或未确认前提的选择。文本说明和上传入口继续保留。
- 每条历史回应必须有 `decision_responses`，具体说明已应用、部分应用或未解决。独立审查须精确覆盖所有方案、修订、回应；“用户选了”不能代替证据审查。无新证据且仍无法判断时应说明停止边界，不自动无限重试。
- 改变分录时，保留 `entries` 原账，另交付 `revisions` 作为整张候选的替代分录；必须引用真实用户回应、原件定位，检查期间和借贷平衡。仅资料范围声明或暂无法判断不能授权修订。Agent 负责解释与重算关联业务和下游结转，独立审查检查完整性。
- 界面展示实际将复核的修订分录，同时可展开原账对照；选择后仍须重新分析和独立审查，之后产生的是待复核草稿，没有正式余额影响。
- 对原件、分录、评估和关联事项完全未变且再次通过独立审查的候选，可沿用此前人工复核，记录来源与审计；任何依据变化则重新复核。老版本没有完整依据指纹的确认不自动继承。
- 老成果保持原结论，可通过“现有资料已全部提供”或“重新审查补证范围”进入新合同处理；不在升级时批量放行已有待补证凭证。

验证和限制详见 `output/stage4-loop-20260923/验证记录.md`。正式交付归档和生产进程隔离仍属于上述既有边界，不由本次改动自动实现。

## 2026-09-25：价税合计关联与跨月处理（合同 v4）

- 禁止按税额凑出发票和付款组合。采购结算以价税合计比较；员工报销以报销总额比较，其他报销组成须有原件，不能把差额猜成补贴。金额吻合仍须核实业务身份和不重复。
- Agent 每次提出关联须交付 `settlement_matches`，服务端按银行付款、发票价税合计及有据组成复算差额。差额未解释或身份未确定只能保留候选，不能声明完整匹配。部分支付和多次结算保留明确边界；不得重复完整结算同一付款或发票。
- 允许跨月搜索，不因发票与付款月份不同就要求人工补件。前期确有未结应付才提出冲销；账内未记应付须说明补记或本期确认方案，不能称为冲销。已有确认政策能决定的处理直接交给凭证复核；政策未知时只提出一次具体处理选择，不自行设小额阈值或改写受保护前期。
- 缩小差旅问题到报销组成及业务归属，不重复索要已提供历史账；没有积极证据不把个人支出或借款当作并列猜测。有据付款可继续处理，其余缺口单独保留。
- 独立审查逐项覆盖 `reviewed_settlement_matches`，从原件复算并检查跨月依据和最小问题。关联变化纳入凭证复核依据指纹，相关候选须重新复核；不自动过账。合同 v3 旧成果保留，可重审生成新版本。

## 2026-09-26：已确认企业差旅规则（合同 v5）

本次仅为荣鼎坤本地账套启用；规则不是通用税务判断，也不授予正式过账权限。

- `EnterpriseTravelPolicy` 复用对象版本存储，按租户、机构、企业、账套隔离，记录生效起始月份、确认来源、服务端确认人/时间及版本。同账套后续月份可复用，其他企业及生效前月份不采用。
- `POST /api/v1/autonomous/travel-policy` 接收完整 `scope`、严格布尔 `enabled`、`expected_version`（首次 0）、`source_note`。使用现有登录、范围、写权限与期间开放门禁；规则内容固定为本次确认口径，不接受客户端伪造确认人或任意规则。版本冲突返回 409，相同版本和内容重复保存不增版。更新有原件的当前期间时自动产生新运行。
- 发票与银行差旅备注支持且金额关联、查重通过的普通交通/住宿，默认采用本企业现有的管理费用—差旅费科目，不再询问详细用途或每日行程。餐费和礼品使用本企业已确认默认分类；明确实际用途可以覆盖默认值，由独立审查核对。科目编码由本企业科目表或历史账确定。
- 补贴、真实重复疑点、历史借款核销和未核实的员工结算分别保留人工事项。收款人与报销人不一致本身不阻断，双方信息仍保留；不得自动核销别人的余额。没有补贴 1000 元自动限额，不能把票款差额猜成补贴。
- 对未点击的处理选项同样审查：企业同意再次支付不构成同一费用重复确认的依据；借款核销必须保留真实银行付款，旧借款余额本身不能阻断无核销关系的正常报销；跨年不能仅凭企业接受就放行本期入费。发现不成立的方案须退回修复，不能以“还待人工确认”掩盖。
- 跨月继续查询历史凭证和未结余额。已记费用且同笔应付未结只提出往来结算，未记费用不能冲不存在的应付；期间事实或跨年处理不明仍人工确认。原账复核保留原分录，调整使用 `revisions`，不改写前期。
- `context.travel_policy` 冻结启用规则，进入执行 Agent、独立审查及输入指纹。`travel_policy_applications` 逐笔记录引用版本、原件、金额关联、分类理由及待确认/已确认事项；确认必须引用同一凭证真实用户回应。补贴、借款核销的门禁及普通差旅的发票付款关联由服务端再校验，业务语义由独立审查核实，不能靠删问题或匹配文字放行。
- 独立审查输出 `reviewed_travel_policy` 和完整应用编号清单。政策支持的候选修订可引用 `policy_application_ids`，但不替代金额或逐笔人工确认。版本变更、停用均改变输入和复核依据，旧结果保留，新候选不能自动沿用旧人工复核。
- 工作台展示当前规则、确认来源、当前结果是否已采用，以及单张凭证的规则版本和剩余人工事项；不新增通用配置页面。

## 2026-09-27：代理记账日常处理与必要确认（合同 v6）

# 票款集中核对（合同 v8，2026-09-27）

当前记账需要、但票据归属或组成未明确的事项，通过 `finding.invoice_matching` 结构归入“票款待匹配”：没找到票据（MISSING）、候选票据归属待确认（CANDIDATE）、归属已确认且金额有差异（AMOUNT_DIFFERENCE）。分类来自执行 Agent 的原件调查，经服务端结构校验和独立审查，不按标题关键字猜测或通过隐藏问题放行。

- 复用原有 bank、invoices、settlement_matches 原件定位。金额由服务端复算；候选票据仅显示候选合计，只有归属确认后才展示确定差额。金额一致不等于归属已确认，差额不自动成为补贴。
- 工作台按资金记录中的收付款对象分组，同一人的多笔款项集中选票或补充说明。未勾选和未填写项目保留；已确认的票据只读展示，不重复要求选择。其他已有依据的凭证可以继续复核。
- `POST /api/v1/autonomous/invoice-matching` 接收 scope、run_id、items（finding_id、invoice_ids、note）及 acknowledged。服务端只接受当前已审查运行中的真实票据 ID；批量校验、存储和新建运行在同一事务完成，过期、跨账套、只读角色、伪造或重复项目均拒绝，失败不留下半批回应。
- `INVOICE_MATCH_SELECTION` 保存作者、时间、原运行、款项、选票快照和用户原始说明。只选票只能说明归属，不能确认补贴、借款核销或完整报销组成；单独填写的业务说明仍须审查实质内容。输入指纹改变后重新分析全部关联业务，并逐项回应，不能直接修改凭证状态。
- 执行和独立审查共享冻结规则；`reviewed_invoice_matching` 精确覆盖全部此类事项。升级使旧候选失效，历史运行、原账及原复核记录保留。只生成待复核草稿，不自动过账。
