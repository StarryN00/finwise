## 0. 这一轮真正要解决的

用户诉求原话：*"财务会提供每家企业的文件可能各有不同，系统没办法做到每个都适配，所以最好的办法还是依靠 agent 去解析成我们需要的目标数据和结构。"*

已确认的真实故障：农行流水**末尾汇总行被当成交易记录**入库，且该记录 `extraction_issues` 为空、`extraction_confidence=1.0`、状态 `PARSED`——**一条看起来完全干净的重复计量记录**。

根因不是 Agent 判断错——**发票和银行流水今天根本不经过 Agent**，全部是 `tabular.py` 的本地规则。汇总行识别是一串写死的字符串精确匹配（`bank_footer_header` 要求 `labels[:4] == ['总收入笔数','总收入金额','总支出笔数','总支出金额']`；通用路径要求整行第一个非空单元格 ∈ `{"合计","总计","小计","本页合计","期初余额","期末余额"}`）。写法一变就漏，且默认动作是**当作数据行往下走**。

**并且：解析器已经把汇总行的数值抓进 `summaries[].reference_rows`（reason=`BANK_TOTAL_VALUES`），然后从未与提取出的明细对过账。** 原件自己写明了答案，程序存下来扔掉了。

- `service.py`：`parse_status` 新增 `RECONCILIATION_FAILED` / `UNATTESTED` / `SOURCE_INTERNALLY_INCONSISTENT`。**`materials.py:123` 的 eligible 判据一个字不改，新状态自动被拦在门外。**

### 算术恒等探针（网 3）—— 这一条单独就能抓住农行 bug

汇总行的金额**按定义**等于其上方全部明细之和。提取完成后、写库之前检查：末尾若干行中是否存在某行的收入金额恰好等于其上方全部记录收入之和。

**不看"合计/总计/本期发生额"怎么写**——`合 计`、`合计：`、`本日累计`、`汇总`、`Total`、全角、以序号或日期打头，全部无所谓。这正是绕开 `tabular.py:803` 那个字符串集合失效点的原因。

误报控制：要求参与求和的行 ≥2 且和 ≠ 0；两个及以上独立信号同时命中（收入合计 + 支出合计，或金额 + 笔数）→ 硬停；单列命中且行形状与主体一致 → 降为待人工判定，既不静默通过也不硬停。

**我没有农行那份原件，未能验证它在这份具体文件上确实命中。P0 第一件事就是拿真实文件验证这条探针，再往下做。**

## 3. 必须一并修的三处现存隐患（设计 §5.4）

### 隐患 1：缓存短路是个定时炸弹
`service.py:320` 的短路条件是 `parse_version == PARSER_VERSION`。**PARSER_VERSION 一升到 v6，一次普通重解析就会用内置启发式静默推平方案解析出的事实。**

改为四元组全等 `(PARSER_VERSION, plan_id, plan_version, sha256)`，且 `plan_origin ∈ {AI, HUMAN, REUSED_FORMAT}` 的事实**永不允许被普通 `parse_artifact` 用内置启发式覆盖**。

### 隐患 2：AI 路径产出的事实，今天大概率过不了「资料核实」——**我已核实机制成立**

`materials.py:297` 的人工核实回放调用：

```python
extracted = extract_workbook(..., ParseOptions(**obj['data']['parse_options']), ...)
```

而 `ParseOptions` **只有 `document_kind` 和 `bank_account_ref`，不携带任何映射/方案引用**。所以回放走内置启发式路径重建事实，然后在 `:309` 要求 `field_sources` 与存库事实**全等**。

银行有专门补救（`:298` 调 `bank_accounts.replay(...)`），**工资表没有对应的 `payroll_mapping.replay(...)`**。而 AI 映射存在的理由恰恰是内置启发式读不对——两者只要一个字段不同就抛 `PreconditionFailed('提取值与当前原件重新校验不一致')`。

另外 `service.py:376` 写下的 `payroll_mapping_id` **全库无人读取**。

**要求：先补一个针对性测试确认这条今天确实是断的**（用一份走过 AI 映射的工资表，尝试资料核实，断言它失败），再随 P1 改成"重读原件 + 取回 plan + 跑同一个执行器"。**不做这一步，P2 的成果基本用不了。**

### 隐患 3：FactRecord 缺出处
新增 `plan_id / plan_version / plan_origin / block_id / rule_id / slot_provenance / attested_by[] / attestation / field_attestation`。没有它，失效判定只能整份原件粗粒度进行，也答不出"这笔凭什么被当成交易""这笔凭什么算核对过"。

## 4. 不可动摇的约束

设计 §1 的五条不变式**写进校验器，不写进 prompt**：

| # | 不变式 | 防什么 |
|---|---|---|
| I1 | 模型不产出任何取自原件的值。契约里没有能装金额、日期、户名、账号、期间、合计数的字段 | 模型成为数据来源 |
| I2 | 自由文本只能用于**排除**，不能用于**纳入**。判成 `DATA` 只能靠结构谓词或服务端封闭词表 | 一条写错的规则最坏是"少一条"，永远变不出假交易 |
| I3 | **未匹配即停**。`default_row_action` 取值域只有 `STOP_UNKNOWN` | `tabular.py:803/806` 的两条静默通道 |
| I4 | 模型只回答 packet 里可直接观测的问题。真实格式、编码、隐藏行、数字格式、行序、金额单位全部本地判定 | 医保 .xls 实为 xlsx、隐藏行、倒序流水、"单位:万元" |
| I5 | 缩放与换算不是转换项，是**停止条件** | 万元/千元/外币被自动换算，4 个数量级的错值 |

另外：

- **复用现有 `parse_artifact` 写入路径，不另建。** `payroll_mapping.py:411` 和 `bank_accounts.py:288/304` 已确立模式：外部算好 `extracted`，交给 `parse_artifact(..., _mapped=extracted, _mapping_id=...)`。版本、`SUPERSEDED`、`_invalidate_source_dependents` 全部自动继承。**"重解析保留旧版本、既有确认失效"已经实现了，不要重建。**
- "解析检查通过" ≠ "人工已核实" ≠ "账务可用"，三者不得合并。
- 无法可靠识别时明确停下，不补造数据；**也不生成"客户缺资料"的待办**——那是把系统错误推给客户。
- 交接说明由本地模板机械渲染，**模型不贡献一个字**，禁止出现"检查通过/资料完整/账务可用"这类结论词（设计 §7 有禁用词单测要求）。

## 5. 上线纪律与运营指标

**P0 先以影子模式（只记录不拦截）跑完一个完整期间，量化误报率，再切换为拦截。**

四个指标随 P0 一起上，并预设失败阈值：

- `override 率`（**>10% 判定方案在实践上失败**）
- `UNATTESTED 占比`
- `D3 平均应答时长`
- `D3 确认后被事后推翻的比例`

**没有这四个指标，不许开 D3。**

理由（设计 §9）：这套设计把"错误率"换成了"打断率"，而打断率是一种**代码里看不见的社会性失效**。200 家企业每月 1000 份文件，15% 落到需要人工指认就是每月 150 次。操作员被问多了会养成"随便点第一个候选"的肌肉记忆——**那一刻八道网全部同时失效**，因为它们最后一环都是"人认真看一眼"。

## 7. 必须如实告知的范围限制

这套设计的检错能力**全部来自原件自带的冗余**，而这份冗余的分布与需求是**反的**（设计 §9）：

- **强冗余**（农行/南京/中行：有合计 + 有余额列）→ 网 3/4/5 全可用，接近可证伪。但这类恰恰是最标准、最不容易出错的文件。
- **零冗余**（客户手工整理的 Excel、按日分段导出的网银、CSV dump）→ 只有结构自证与行准入，**零独立检错**。而这类正是用户说的"每家各有不同"、真正需要 Agent 的那批。

**后果**：强冗余文件因为网多判据严，反而更容易触发告警，消耗掉操作员的注意力；零冗余文件安静地落 `UNATTESTED`，两周后没人再看那个黄标签。**打断的分配是反的。**

因此 `UNATTESTED` **不能只是一个标签**，必须携带可执行的抽样规则（如"首尾各 3 行 + 金额 Top 5 + 随机 3 条"），且抽查完成率进运营看板。同时要主动压掉强冗余文件的假警报（软层漂移不阻断、页小计不裁决、浮点判 `FLOAT_REPRESENTATION_ONLY`、跨月走 `RECONCILED_OUT_OF_PERIOD` 而非 `FAILED`）——**每压掉一个假警报，就是给零冗余文件多留一份注意力**。

**这套设计兑现的是**：解析结果可审计、错了不静默、识别不了会停下来问你且问得具体。
**没有兑现、也不认为任何设计能兑现的是**：在原件不提供任何自我证明的情况下，自动保证这批数据是对的。

## 8. 一个必须避开的陷阱

**原表汇总常常覆盖跨月数据，不能直接与本期筛选结果相比。** 对账必须在"解析出的全量"这一层做，再做期间切分；两个数分开存。否则一次正确的解析会被判成故障（设计 §4.9 有两级对账的完整规则）。
