## 2026-09-07 对话式资料办理与按需建议

本节替代上一轮只有统一表单的交互。现有资料任务统一进入逐步引导：问题摘要 → 选择／回答 → 确认摘要 → 用户明确提交。原件对照按需展开，核实记录时仍须查看并勾选本页记录。选项内 `steps` 定义问句及字段范围，前端只展示当前步骤；修改已答内容后重新核对摘要。选择、前进、返回及自然语言说明本身不执行业务命令。

- 明确规则直接引导，不自动调用模型。
- 用户主动请求时，经现有 `/api/v1/agent/suggestion` 的 `MATERIAL_GUIDANCE` 阶段获取建议，使用原 Gateway。请求绑定完整 Scope、task_id、descriptor_hash 与 request_id。
- 模型只看到白名单化的问题类型、字段缺失／异常情况及服务端声明的可用选项，不发送文件名、原始单元格、企业／人员名称、银行账号、发票号或用户备注。因脱敏上下文有限，不能据此推定实际业务事实。
- 响应只允许已声明选项或空选项、理由、不确定点及置信度；本轮 `prefill` 必须为空，不预填日期、科目、账户等业务事实。低置信度或无法匹配选项转人工，不发明新动作。用户仍须自行选择，并在提交摘要确认。
- 失败、无可用选项可沿用规则入口，或通过原单原因暂缓记录保留立场；未知情况不会被强行核实或自动放行。
- ModelRun 保存版本绑定、脱敏输入、输出、模型／Prompt／Schema、哈希、耗时及用量。同 request_id 幂等，调用期间输入变化则拒绝建议。资料办理建议在处理记录中单列，不混入既有业务模型覆盖。
- 写入仍由原资料、发票、票据及银行命令校验权限、期间、版本与门禁；未引入批量处理、自动制证、外部导出或 Agent 执行器。历史期初及业务复核等原有专门工作流不自动迁入此次资料任务契约。

## 2. 信息结构

1. 企业、账套、期间上下文：仅完整显示一次，切换隔离服务端数据和临时表单。
2. 阶段进度：醒目百分比和五阶段；明确是已完成阶段数 / 5，不代表数据核实率。
3. 资料结构：期初与历史衔接 / 本期业务资料 / 归属或用途待确认。每份有效原件只归入一个节点。
4. 当前任务：默认展开。问题、影响、已有依据、完成条件、直接处理表单依次出现。
5. 已有成果：始终可见摘要；分别列出已提取、业务校验通过、人工核实和本地凭证复核的证据，不用一个笼统的绿色“可用”替代。
6. 资料详情、业务对象、凭证、处理记录：次要查看入口，按需展示，不把通用上传和全部原件列表铺在首屏。

资料结构中，本期资料按采购及入库、销售、银行与票据、薪酬及税费分类。归类来自保存的用途、解析类型和期间，不凭企业名或文件名猜测。

跨期资料不自动成为期初余额。例如二月电子承兑只能先进入“归属或用途待确认”；选择为基线来源须由用户主动指定，并通过原有工作簿及余额核对。

## 3. 信任与计数口径

| 展示 | 证据要求 | 允许表达的用途 |
|---|---|---|
| 已提取，待核实 | 当前有效原件、事实记录、行/单元格定位 | 可查看提取结果；不表示业务正确 |
| 需核对提取结果 | 字段缺失、金额/方向异常等解析问题 | 按来源与同类原因合并查看，不把每条记录变成独立待办 |
| 期间需确认 | 事实期间校验未通过 | 查看原件，核对归属；不得混入本期可用成果 |
| 业务校验通过 | 基线有效、当前版本确定性对账通过、无重复归属 | 可进入该业务的后续处理；不等于可导出 |
| 期初已人工核实 | 基线当前有效，责任人、时间、来源与逐行比较可追溯 | 可用于本期账务衔接 |
| 凭证已本地复核 | 凭证复核记录及当前来源绑定仍有效 | 本地复核成果；不等于外部入账 |

原件份数、事实条数、问题类别、阻断业务组数分别计数。同一事实可有多个问题，问题明细数量不可相加充当事实总数。跨期记录属于原文件的引用，不额外算一份文件。来源作废或版本变化时，不能复用旧绿色成果。

模型覆盖单独显示：成功真实调用次数、当次输入事实数、模型和任务类型。历史模型输入缺少版本绑定时明确是“调用时覆盖”，不推断为当前已核实。模型返回建议不改变数据核实状态。

## 4. 当前任务与操作

任务优先级：无本期资料 → 接收资料；基线无效 → 期初衔接；未解析资料 → 解析；提取/期间问题 → 查看并定位原始依据；业务阻断 → 补证；候选规则 → 审阅；业务校验通过 → 凭证复核/交付。

期初任务区分“未提供原件”和“已接收、用途或解析待核对”：历史 / 期初分类已有未指定用途的有效原件时，显示已接收份数及待处理状态，主操作为“查看已上传账表”，不再将槽位未指定表述为文件未上传。列表中保留原件期间、用途和提取状态，解析失败明确展示原因。不凭文件名推断用途，不自动把历史账表填入基线槽位。

期初余额、紧邻上期末余额 / 结账资料仍是两个独立用途槽位。没有可供核对的相关原件时，才优先提供添加入口；选择、查看或提取原件不等于基线确认。已有原件不能满足用途或格式条件时，先明确具体缺口，再补充所需资料。两侧来源明确后才能生成对比。

对比展示科目、期初/上期末借贷、行差异和原件定位。通过后仍须主动勾选“已核对完整性及来源”再确认。缺行、差额、用途错误不允许确认。只保存附件、记录备注或查看问题均不消除阻断。

其他问题按来源与原因展示受影响记录、原始值/提取值、建议补充内容和下一步。补充资料使用原件追加链路；不新增“已看过即放行”按钮。业务分组、校验、凭证等已有命令入口保留为次要处理工具。

本节接续第 8 节，实现此前尚未接通的后台处理。边界仍为独立项目、本机 Staging；不修改原件、不自动确认基线、不生成凭证，不调用模型猜测金额，也不扩大到全部一月资料解析。

### 自动流程与人工边界

- 上传用途为 `historical_reference` 的原件后，服务端自动建立 `HistoricalPreparation`。启动时补扫此前已接收但未入队的历史原件，客户端不负责触发计算。
- 后台状态：排队 → 处理中 → 等待另一份账表 / 待选择来源 / 有问题待核实 / 待人工确认 / 失败。文件用途从表内标题和列结构识别，期间从表内起止月份识别；未知结构保留原件并给出错误，不按文件名猜测。
- 目前支持实际试点的“科目余额表六金额列＋序时账”XLS/XLSX 结构；多工作表、无法明确单位、金额非法、期间不衔接等情况拒绝自动形成可确认结果。
- 明示币种必须为人民币；同格多行币种冲突、分录/合计/页脚外币金额均拒绝进入候选，不自动换算。仅写“单位：元”的原件仍须由人明确确认人民币口径的最终结账版本。Excel 数值型整数科目编码规范为整数文本，文本前导零保留；小数、布尔和超精度编码拒绝处理。
- 系统校验科目余额等式、父子净余额及发生额、表内合计、逐张凭证借贷、逐科目发生额及可定位的单维辅助明细。上年期末数只形成下月期初**候选**，上年年初数和历史分录不会写入本期事实。
- 一级科目合计可能抵销其借贷明细，与末级科目不抵销合计不同。页面分别标明两个口径、各自借贷金额，基线采用末级明细，不同时汇总父级。
- 有未知科目或辅助明细缺口时保留问题，不因总额平衡、发生净额归零或点击“查看”而放行。补充版本后明确选取本次两份账表，再重算。
- 无阻断时，人工分别确认“最终结账版本”“科目和辅助明细完整性”“按期末结转期初”，之后经原有 `confirm_baseline` 命令生成已确认基线。普通手填余额不能绕过历史来源门禁；后台不能代替这三项声明。

### 状态、审计与页面

- 队列与结果使用已有追加式对象版本，无新数据库表。领取任务在事务内，解析在事务外；300 秒租约、最多 3 次中断恢复，后续由人重试。新输入或新租约令旧结果失效，发布前再次核验期间及原件。
- 保存输入原件 ID / 版本 / 哈希、解析版本、处理次数与时间、校验和候选行；审计包含输入输出哈希及失败原因。原件字节与原有事实版本保持不变。

## 11. 历史问题处理：补证、提交方案、记录无法补充

目标是让已经看懂问题的用户能够提交处理决定，而不是只能反复查看或上传。本轮为当前真实工作台增加问题处理记录，不替换基线校验器，不实现凭文字自动调账或财务例外放行。

### 交互合同

- 有历史核对问题时，当前任务只提供一个主入口“处理 N 项核对问题”。移除任务页尾和全局导航重复的历史上传链接；无历史任务、等待另一份账表等接收场景仍保留一个可达入口。
- 问题详情按事项选择，直接保留事实、金额、来源与建议，处理区提供“补充材料 / 依据现有资料提交方案 / 暂无法补充”。只有当前选择的路径显示主操作。
- 补充路径展开明确的上传按钮，复用不可变原件接收、选择正确版本和后台重算；不覆盖已有文件。上传后的选择/核对结果不等于原问题自动关闭。
- 方案路径填写核实结论、拟处理方案、责任人和后续安排，关联本次核对已绑定历史账表的具体来源行。提交后显示待复核，不显示已解决。当前仅支持绑定账表内定位；其他格式的证明材料不会被当作可自动校验的历史余额。
- 无法补充路径仅填写无法取得材料的原因（必填，1–2000 字），无需附件、处理方案或后续安排。责任人由服务端按当前登录身份记录，前端只读显示，不接受客户端指定责任人。不提供“接受风险并强制通过”；记录后保留未解决问题，不重复要求上传。
- 两条记录路径先显示影响预览：原件、金额、科目及期初均不变；当前问题尚未解除。提交、重复提交、失败和冲突均给可见反馈。
- 会计、复核员或管理员可以复核另一位用户提交的方案，并填写复核意见；原提交人不能自审。复核可通过或退回。通过只代表处理方案获认可，不代表账表校验通过；执行需要的资料更正仍由相应合法来源及原有命令门禁处理。
- 原提交人可以修订记录；修订后重新进入待复核，旧意见保留在对象历史版本中。无权限、已关闭期间及过期来源均不可写。其他人不可覆盖提交人的说明。
- “暂无法补充”修订仍保持已记录状态，不进入方案复核。其记录摘要只展示原因、责任人与记录时间；旧版扩展字段保留在已有版本及审计记录中，不迁移或覆盖。新记录不制造处理计划与后续安排。
- 提供“继续整理本期资料”次要入口，只导航到资料清单，不改变办理阶段，不允许依赖未确认基线的制证或交付。

### 状态及数据合同

- 使用追加版本对象 `HistoricalIssuePlan`，不新增数据库表。关联完整 Scope、历史任务 ID/版本、输入哈希、稳定问题键、原问题快照、依据文件版本/哈希/具体行。
- 状态为待复核（SUBMITTED）、暂无法补充已记录（UNAVAILABLE_RECORDED）、方案复核通过（REVIEWED）、退回补充说明（RETURNED）。它们独立于原问题状态；不得加入阶段完成数或伪装为已核实余额。
- `save_historical_issue_plan` 以历史任务为目标，携带预期方案版本；`review_historical_issue_plan` 以方案当前版本为目标。沿用命令权限、幂等、事务、开放期间与审计机制。
